This document defines the feature contract for the architecture work: we can change internal implementation and even reshape features, but the user must keep the same convenience or get a better one. The core promise is: discover a title, find a reliable source, play it quickly, resume later, manage watched/library state, and use debrid/torrent/subtitle/player integrations without thinking about the transport details.

Kinema is not only a torrent player and not only a media catalog. It is a native desktop watching workflow: find → choose source → play/download → continue → track progress. The refactor should protect this workflow first.

A useful way to think about the architecture: user features should depend on capabilities, not on concrete subsystems. For example, auto-next needs a file catalog, not specifically libtorrent.

It should coordinate resume, transfer/session opening, player launch, and progress tracking through ports. UI actions should not know torrent/debrid/local-server details. Play cache and saved downloads are two policies over the same transfer/session model. The user sees “play now” and “save offline”; the architecture sees OnDemand vs Full and Ephemeral vs Pinned. Libtorrent, Real-Debrid, AllDebrid, and future sources should all produce a byte-range source plus optional file catalog. The player and history code should not care which one. Progress tracking should listen to player/session events and write history. It should not own resume orchestration or call stream actions directly. Current episode, stream ref, file index, file catalog, previous/next targets, and user-close behavior should be represented as one playback session model rather than inferred across multiple controllers.

These are product questions, not implementation questions. Answering them lets us decide where simplification is safe.

  1. Should backend override stay visible on every stream row, or move into an advanced menu?
  2. When the exact saved release is unavailable, should resume automatically choose a similar stream?
  3. Should “Downloads” and “Playback cache” remain visually separate concepts, or should the UI say “Saved offline” vs “Temporary cache”?
  4. Should season-pack auto-next be automatic by default, or should users explicitly enable it per session?
  5. Should torrent-only users and debrid users see different simplified settings pages?
  6. Should external-player playback be treated as first-class for progress tracking, or best-effort as it is today?

The architecture proposal should be rewritten as a response to this feature contract: each proposed boundary must explain which user capabilities it protects, which features it simplifies, and how we prove parity through tests.
