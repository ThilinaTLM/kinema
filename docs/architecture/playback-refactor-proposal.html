The current system already has useful abstractions (AssetSession, DownloadBackend, PlaybackContext, stores/controllers), but several classes still act as multi-purpose coordinators. The proposal is to keep Qt/QML and QCoro, keep all features, and evolve toward a small application-use-case layer with explicit ports: PlayerPort, MediaSourcePort, StreamGatewayPort, PlaybackHistoryRepository, and DownloadRepository. Concrete adapters remain mpv, libtorrent, debrid, SQLite, and localhost HTTP.

  • Embedded mpv player and QtQuick chrome.
  • Localhost Range streaming model.
  • Unified AssetSession-style byte source abstraction.
  • Real-Debrid / AllDebrid / torrent backend parity.
  • Continue Watching, watched state, resume, subtitles, MPRIS, series auto-next.
  • Split orchestration out of large managers/controllers.
  • Hide torrent-specific DTOs from generic download headers.
  • Replace controller-to-controller cycles with application use cases.
  • Move policy decisions into small pure services.
  • Delete legacy torrent-local server after tests are migrated.
  • No big-bang rewrite.
  • No global event bus as a substitute for clear ownership.
  • No migration of the user database/config as part of this work.
  • No QML-facing churn unless a boundary leak forces it.

Introduce a cohesive application layer for user workflows and keep infrastructure behind ports. Controllers/view-models become thin adapters. Existing concrete code is migrated behind those ports incrementally.

The current pipeline works, but feature growth has pushed several classes beyond one reason to change. These are the coupling seams worth addressing first.

The wiring is fragile because ownership, cross-service subscriptions, and feature-level routing all happen in one constructor. It is a UI action façade, but it also decides playback path, consults history, calls downloader, supports torrent legacy paths, and launches players. That makes a simple menu action depend on too many subsystems. It owns backend selection, sessions, local HTTP server, persistent rows, live stats, recovery, attach/detach semantics, and pin/eviction policy. It is cohesive around downloads, but too broad to test or modify safely. It is both the libtorrent adapter and a policy engine: file selection, startup buffer, sliding-window priorities, stats, cache/touch semantics, and a legacy local server. The target is not "more layers" for their own sake. The target is explicit direction of dependencies: UI calls application use cases; use cases depend on small ports and pure policies; infrastructure implements ports. The domain objects remain simple C++ values.

This is a hexagonal architecture in a Qt shape: application services may still be QObjects and may expose signals for QML, but their dependencies are ports, not concrete mpv/libtorrent/debrid/SQLite classes.

The single entry point for "play this stream/context". It obtains a playable URL from TransferUseCase, asks ResumeUseCase for a resume point, starts the player through PlayerPort, and publishes session lifecycle events.

Replaces the broad center of DownloadManager. It opens/reuses sessions, upgrades OnDemand to Full, pins/unpins, pauses/resumes, and asks StreamGatewayPort for a local URL. It delegates storage and telemetry to smaller collaborators.

Owns progress persistence, watched finalization, and track-memory snapshots. It consumes typed player/session events rather than being wired directly to a player window.

Owns previous/next episode targets for the active playback session. It obtains file lists through a generic SessionFileCatalog instead of knowing whether they came from libtorrent or a debrid resolver.

Owns the TCP server only. It maps token → ByteRangeSource, parses Range requests, enforces backpressure, and emits request telemetry. It does not know downloads, debrid, torrents, history, or players.

TorrentMediaSource, RealDebridMediaSource, and AllDebridMediaSource all implement the same MediaSourcePort and produce a PlayableAssetSession / ByteRangeSource.

The following ports are intentionally small. They are not meant to abstract Qt away; they abstract feature boundaries away from concrete infrastructure.

// Application-facing player capability. class PlayerPort { public: virtual ~PlayerPort() = default; virtual void play(QUrl url, domain::PlaybackContext ctx, std::optional<qint64> resumeSeconds) = 0; virtual void stop(domain::PlaybackEndReason reason) = 0; virtual PlayerSnapshot snapshot() const = 0; // In Qt this can remain signals on a QObject-derived adapter. // Conceptually: fileLoaded, positionChanged, durationChanged, endOfFile, error, tracksChanged. }; // Backend-agnostic source of playable bytes. class MediaSourcePort { public: virtual ~MediaSourcePort() = default; virtual bool canOpen(const domain::Stream& stream) const = 0; virtual QCoro::Task<std::unique_ptr<PlayableAssetSession>> open( const domain::AssetRef& ref, const domain::Stream& stream, const domain::PlaybackContext& ctx, domain::DownloadMode mode) = 0; }; // Local URL provider. Implementation is localhost HTTP today. class StreamGatewayPort { public: virtual ~StreamGatewayPort() = default; virtual QUrl expose(QString assetId, ByteRangeSource& source) = 0; virtual void revoke(QString assetId) = 0; }; class ByteRangeSource { public: virtual ~ByteRangeSource() = default; virtual QString fileName() const = 0; virtual qint64 size() const = 0; virtual QCoro::Task<bool> ensure(ByteRange range) = 0; virtual QByteArray read(ByteRange range) const = 0; };

A port can be introduced as an abstract C++ class first and only later moved to a cleaner folder. The first milestone should be behavioral containment, not perfect directory structure.

Keep PlayerWindow, PlayerViewModel, and MpvVideoItem. Add a small EmbeddedMpvPlayerAdapter that implements PlayerPort and owns the signal translation. Then application code no longer needs to know about PlayerWindow directly.

  • Move out: resume prompt orchestration, load watchdog policy, moviehash kickoff.
  • Keep in player: mpv commands, track/chapter parsing, QtQuick chrome state.
  • Benefit: external player support can use the same PlaybackUseCase path where possible.

Rename the role, not necessarily the class immediately: LocalMediaServer becomes the implementation of StreamGatewayPort. It should depend on a ByteRangeSource interface only.

  • Remove knowledge of AssetSession subclasses from server code.
  • Keep Range parsing, 206/416 responses, chunk writes, and backpressure exactly as-is.
  • Make request logging/telemetry generic: assetId, range, wait ms, bytes served.

RiskWhy it mattersMitigation
Playback regressions mpv/loadfile/Range interactions are timing-sensitive. Keep LocalMediaServer and MpvVideoItem behavior unchanged until ports are stable; add integration tests around Range serving and end-of-file.
Async lifetime bugs QCoro tasks can outlive QObject owners during teardown. Continue using epoch counters and QPointer guards; centralize task ownership in use cases.
Architecture over-abstraction Too many interfaces can make a small app harder to navigate. Only introduce ports where there is a real infrastructure boundary or existing cyclic dependency.
QML churn View-model changes are visible and easy to break. Keep current controllers as façades while moving internals behind them.
Feature parity drift Auto-next, resume, debrid file lists, and stream-size hydration rely on subtle state. Represent playback session state explicitly and test one path per backend.
No production code uses src/torrent/LocalStreamServer; tests use the generic stream gateway. DownloadManager public API is either a thin façade or replaced by TransferUseCase. StreamActions::play() no longer knows about torrent vs downloader vs player launcher details. HistoryController no longer fetches indexer streams or calls StreamActions; one-click resume lives in ResumeUseCase. Torrent-specific file-list types do not appear in generic download/session headers. Watched/resume/backend/file-selection/priority policies have focused unit tests without Qt windows or libtorrent. The end-user feature set is unchanged: embedded playback, external playback, debrid, torrents, local HTTP streaming, downloads, resume, watched state, subtitles, MPRIS, and series auto-next all still work.

If we want a low-risk first PR that proves the direction, start here:

  1. Create application/transfer/ports/ByteRangeSource.h and adapt AssetSession to implement it.
  2. Rename the conceptual role of LocalMediaServer by adding a thin StreamGatewayPort interface and a LocalHttpStreamGateway adapter that delegates to the existing server.
  3. Change DownloadManager to depend on the gateway interface internally. Public API unchanged.
  4. Add tests for LocalMediaServer through the gateway with a fake byte-range source.

This slice decouples the most stable boundary — HTTP Range serving — without touching mpv, libtorrent, debrid credentials, QML, or database schema.
